# Verulam CC iCal

[![Build And Publish](https://github.com/davidcollom/vcc-ical/actions/workflows/build-and-publish.yaml/badge.svg)](https://github.com/davidcollom/vcc-ical/actions/workflows/build-and-publish.yaml)
[![GitHub issues](https://img.shields.io/github/issues/davidcollom/vcc-ical)](https://github.com/davidcollom/vcc-ical/issues)

Turns the [Verulam Cycling Club](https://www.verulamcc.org.uk/) events calendar
into an **iCalendar feed**, so the club's events can be subscribed to from any
calendar app, home automation system or script.

**Live feed:** <https://vcc-ical.pages.dev/events>

| | |
| --- | --- |
| Feed URL | <https://vcc-ical.pages.dev/events> |
| Index page | <https://vcc-ical.pages.dev/> |
| Format | iCalendar 2.0 (RFC 5545), served as `application/octet-stream` |
| Refreshed | Nightly at 01:15 UTC, plus on every push to `main` |
| Coverage | The current month and the two months after it |
| Built with | [Middleman](https://middlemanapp.com/) 4.6.3, Ruby 3.4 |

## What it does

Verulam Cycling Club (VCC) is based in St Albans, Hertfordshire. It is one of
the oldest and most active cycling clubs in the county, with over 450 members
across road racing, cyclocross, track, time trial, audax and sportive riding,
off-road riding and youth racing. The club's website lists everything it is
doing — club runs, midweek rides, off-road Thursdays, youth cyclocross
sessions, track sessions, hill climbs and club nights — but only as a web
page, with no way to subscribe to it.

This project turns that web page into a feed:

1. Fetches the **current month** and the **two months after it** from
   `https://www.verulamcc.org.uk/events-calendar/month.calendar/`.
2. Scrapes the event markup with **Nokogiri** and turns each event into an
   iCalendar `VEVENT`.
3. Serves the result as a single static `.ics`-style document at `/events`.

The whole site is generated by [Middleman](https://middlemanapp.com/), a static
site generator. The only real output is the feed plus a one-line index page
linking to it.

Because the scraper only looks at the current month and the two after it, the
feed is a rolling window of upcoming club activity rather than an archive.

```
                 ┌──────────────────────────────────────────┐
  verulamcc.org.uk│  events-calendar/month.calendar/YYYY/MM  │
        ─────────▶│  (JEvents HTML, 3 months)               │
                 └────────────────┬─────────────────────────┘
                                  │ Nokogiri scrape
                                  ▼
                 ┌──────────────────────────────────────────┐
                 │  verulam_cal.rb                          │
                 │  VerulamCal.find_events → Icalendar      │
                 └────────────────┬─────────────────────────┘
                                  │ to_ical
                                  ▼
                 ┌──────────────────────────────────────────┐
                 │  source/ical.erb  ──proxy──▶  /events     │
                 └────────────────┬─────────────────────────┘
                                  │ middleman build
                                  ▼
                 ┌──────────────────────────────────────────┐
                 │  build/  ──▶  Cloudflare Pages           │
                 │               https://vcc-ical.pages.dev │
                 └──────────────────────────────────────────┘
```

## Using the calendar

### In a calendar app

Paste <https://vcc-ical.pages.dev/events> into your calendar app:

| App | How to subscribe |
| --- | --- |
| **Google Calendar** | Gear → *Settings* → *Other calendars* → *Add calendar* → **From URL** → paste the URL → *Add calendar* |
| **Apple Calendar** (macOS / iOS) | *File* → *New Calendar Subscription…* → paste the URL |
| **Outlook** (Windows / new Outlook / Mac) | *Add calendar* → **Subscribe from web** → paste the URL |
| **Thunderbird** | *File* → *New Calendar…* → *Add a Calendar* → **Network Subscriptions** → *URL* → paste the URL |
| **Proton Mail** | *Settings* → *Integrations* → *Calendar* → paste the URL |
| **Fastmail** | *Settings* → *Calendars* → *Add a subscribed calendar* → paste the URL |

The subscription is refreshed periodically by the client — Google Calendar and
Outlook poll roughly once a day, and the other clients follow a similar
schedule. The feed itself is regenerated every night, so a change on the club
website appears within about a day.

> **Times are floating local times.** Events are emitted without a timezone
> identifier (`DTSTART:20261001T190000`, no `Z` and no `TZID=`). Most clients
> interpret a floating time in *the viewer's* timezone, so the same event can
> appear at a different wall-clock time depending on where you are. The times
> are the club's local times (Europe/London).

### On a website

```html
<a href="https://vcc-ical.pages.dev/events">Subscribe to Verulam CC events</a>
```

### From the command line

```bash
# Save the feed
curl -sSL https://vcc-ical.pages.dev/events -o verulam.ics

# List the next few events
curl -sSL https://vcc-ical.pages.dev/events \
  | grep -E '^(SUMMARY|DTSTART)' \
  | paste - - \
  | head
```

### From code

**Python** — [`icalendar`](https://pypi.org/project/icalendar/):

```python
from urllib.request import urlopen
from icalendar import Calendar

cal = Calendar.from_ical(urlopen("https://vcc-ical.pages.dev/events").read())
for event in cal.walk("VEVENT"):
    print(event["DTSTART"].dt, event["SUMMARY"])
```

**Ruby** — the same [`icalendar`](https://rubygems.org/gems/icalendar) gem this
project uses:

```ruby
require "icalendar"
require "open-uri"

cal = Icalendar::Calendar.parse(URI.open("https://vcc-ical.pages.dev/events").read)
cal.events.each { |e| puts "#{e.dtstart} #{e.summary}" }
```

**JavaScript** — [`ical.js`](https://github.com/mozilla-comm/ical.js):

```js
import ICAL from "ical.js";

const response = await fetch("https://vcc-ical.pages.dev/events");
const jcalData = ICAL.parse(await response.text());
const comp = new ICAL.Component(jcalData);
for (const event of comp.getAllSubcomponents("vevent")) {
  console.log(event.getFirstPropertyValue("summary"));
}
```

**Home Assistant** — use the [`ical`](https://www.home-assistant.io/integrations/calendar/) integration:

```yaml
calendar:
  - platform: ical
    url: https://vcc-ical.pages.dev/events
    name: Verulam CC
```

which every common version manager understands as "the latest 3.4.x".

### 2. Install the gems

```bash
bundle install
```

Bundler reads the `ruby '~> 3.4.0'` requirement in the `Gemfile` and will
refuse to run against a Ruby outside the 3.4 series.

### 3. Run the preview server

```bash
bundle exec middleman server
```

Then open:

| URL | What it is |
| --- | --- |
| <http://localhost:4567/> | the index page |
| <http://localhost:4567/events> | the generated calendar feed |

The server defaults to port **4567**; override it with `--port`:

```bash
bundle exec middleman server --port 3000
```

The preview server re-generates the feed on every request, so it always
reflects the live club calendar.

### 4. Build the static site

```bash
bundle exec middleman build
```

The static site is written to `build/`. Preview it with any static server:

```bash
cd build && python3 -m http.server 4567
```

or

```bash
npx serve build
```

### 5. Check the feed

```bash
curl -s http://localhost:4567/events | head -5
curl -s http://localhost:4567/events | grep -c 'BEGIN:VEVENT'
```

## Deployment

The site is deployed to **Cloudflare Pages** by the
[`build-and-publish.yaml`](.github/workflows/build-and-publish.yaml) workflow.

| Trigger | Effect |
| --- | --- |
| `schedule` — `15 1 * * *` | Nightly rebuild and publish (this is what keeps the feed fresh) |
| `push` to `main` | Rebuild and publish |
| `pull_request` to `main` | Rebuild only — the deploy step is skipped for `dependabot[bot]`, and preview deployments use the PR branch |
| `workflow_dispatch` | Manual rebuild |

The workflow:

1. checks out the repository,
2. sets up Ruby with `ruby/setup-ruby@v1` and `bundler-cache: true`,
3. optionally joins the Tailscale tailnet (only if `TS_CLIENT_ID` and
   `TS_SECRET` are configured),
4. runs `bundle exec middleman build --verbose`, wrapped in
   [`nick-fields/retry`](https://github.com/nick-fields/retry) with up to 10
   attempts (the scrape depends on a third-party website being up),
5. deploys `build/` to the Cloudflare Pages project `vcc-ical` using
   `wrangler pages deploy`.

### Required secrets

| Secret | Required | Purpose |
| --- | --- | --- |
| `CLOUDFLARE_API_TOKEN` | yes | Cloudflare API token used by Wrangler |
| `CLOUDFLARE_ACCOUNT_ID` | yes | Cloudflare account ID |
| `TS_CLIENT_ID` | no | Tailscale OAuth client ID; enables the tailnet step |
| `TS_SECRET` | no | Tailscale OAuth secret |

### Local deploy

```bash
npm install -g wrangler
wrangler pages deploy build --project-name=vcc-ical --branch=main
```

### A second, unrelated workflow

[`regular-commit.yaml`](.github/workflows/regular-commit.yaml) rewrites
`.metadata` with the current timestamp every five days. It exists purely to
give the repository a steady stream of activity.

## How it works

### Fetching the calendar

[`config.rb`](config.rb) mounts three remote sources with the
`middleman-data_source` extension:

```ruby
activate :data_source do |c|
  c.root  = "https://www.verulamcc.org.uk/events-calendar/month.calendar/"
  c.sources = [
    { alias: 'current_month',       path: Date.today.strftime('/%Y/%m/%d/-'), type: :html },
    { alias: 'next_month',          path: Date.today.next_month.strftime('/%Y/%m/%d/-'), type: :html },
    { alias: 'month_after_next',    path: Date.today.next_month.next_month.strftime('/%Y/%m/%d/-'), type: :html }
  ]
  c.decoders = { html: { extensions: [''], decoder: ->(src) { VerulamCal.find_events(src) } } }
end
```

The three months are concatenated:

```ruby
proxy "/events", "ical", locals: { e: VerulamCal.new(
  @app.data.current_month + @app.data.next_month + @app.data.month_after_next
) }
```

`config.rb` also patches `Net::HTTPHeader` to send a fixed `User-Agent` and
`Accept` header, which the club's site expects.

### Scraping the events

[`verulam_cal.rb`](verulam_cal.rb) holds the scraper.

* `VerulamCal.find_events(html)` parses the page with Nokogiri, selects every
  `div.eventstyle` element, skips anything whose text contains `CANCELED`, and
  pulls the title and the date range out of the popup's `title` and
  `data-bs-content` attributes.
* Two regular expressions recognise the date formats:
  `DATE_REGEX` for single-day events and `MULTI_DATE_REGEX` for multi-day
  ones.
* Each event gets a stable `UID` — the first 21 hex characters of a SHA-256
  digest of the event's HTML — so calendar clients recognise it as the same
  event across rebuilds and can update it in place.
* `VerulamCal#to_ical` renders the `Icalendar::Calendar` as an iCalendar
  string.

### Serving the feed

```ruby
proxy "/events", "ical", locals: { e: ... }
```

Middleman's `proxy` directive renders `source/ical.erb` and writes the result
to `/events` in the build output. `source/ical.erb` is a single line:

```erb
<%=e.to_ical%>
```

`source/index.html.erb` is the index page, with a single link to `/events`.

## Keeping the Ruby version in sync

Five places mention the Ruby version, and they must agree:

| File | Value | Why |
| --- | --- | --- |
| `.ruby-version` | `3.4` | The series. `ruby/setup-ruby` and every local version manager read this. |
| `Gemfile` | `ruby '~> 3.4.0'` | The requirement Bundler enforces against the running Ruby. Must be a **range**, not an exact patch, or Bundler rejects the runtime. |
| `Gemfile.lock` → `RUBY VERSION` | `ruby 3.4.12p0` | Informational only — Bundler does not enforce it in frozen mode. |
| `Dockerfile` | `FROM ruby:3.4` | The base image. `ruby:3.4` is a rolling tag that tracks the newest 3.4.x. |
| `.github/dependabot.yml` | `versions: [">= 3.5.0"]` | Stops Dependabot from bumping the Docker base image onto a series the `Gemfile` does not allow. |

**Moving to a new series (say 3.4 → 3.5) means changing all five in one
commit**, and moving the Dependabot `ignore` range to the *next* series
(`>= 3.6.0`).

Two rules learned the hard way:

* **Do not pin an exact patch release.** Runner images only carry prebuilt
  Rubies for recent patches of each series. Pinning `3.4.1` worked on
  `ubuntu-24.04` and 404'd the moment `ubuntu-latest` moved to `ubuntu-26.04`
  (see [actions/runner-images#14748](https://github.com/actions/runner-images/issues/14748)).
  Pin the *series* and let the tooling resolve the newest patch.
* **Dependabot cannot group updates across package ecosystems.** It has no
  concept of the `bundler` ecosystem's Ruby version, so it cannot know that
  `FROM ruby:…` and `ruby '~> 3.4.0'` have to move together. The `ignore` rule
  in `.github/dependabot.yml` is what keeps them aligned.

## Known issues

* **The Docker image cannot serve the site.** `Dockerfile` runs
  `puma config.ru`, but this project is a static site with no `config.ru` in
  the repository. The image builds, but `make local` will not start a working
  server. `make publish` also targets `davidcollom/vcc-cal`, which is not
  published on Docker Hub.
* **`pry` is required unconditionally.** `verulam_cal.rb` has a top-level
  `require 'pry'`, so `bundle install --without development` produces a
  project that cannot boot.
* **The feed is served as `application/octet-stream`.** The output path has
  no `.ics` extension, so Cloudflare Pages cannot infer a calendar content
  type. Every major client still accepts it, but a stricter client may
  prefer a `text/calendar` response.
* **Multi-day events collapse to a single day.** `MULTI_DATE_REGEX` captures
  the start date and the end *time*, and the end timestamp is built from the
  start date, so a two-day event shows as one day.
* **The scrape depends on a third party's HTML.** If the club changes its
  calendar markup, `find_events` will stop matching events. The
  `nick-fields/retry` wrapper in CI covers transient network failures, not
  markup changes.
* **Event times are floating.** See [Using the calendar](#using-the-calendar).
